# init - 蓝图层初始化

## 目标

为项目建立 `.blueprint/` 结构，让 explore 和 align 有蓝图可用。

## 核心思路

渐进式生成：init 只负责根蓝图和模块入口蓝图，文件级蓝图由 align 在会话结束时沉淀。

## 执行步骤

1. 扫描项目目录结构，识别技术栈、项目类型和主要代码目录。
2. 识别模块边界：
   - 优先按 manifest 文件划分（package.json、go.mod、Cargo.toml、pyproject.toml 等）
   - 其次按顶层源码目录划分（src/、app/、lib/、packages/ 等）
   - 对于 monorepo，每个 package 或 app 视为独立模块
   - 含 3+ 代码文件且职责内聚的目录也视为模块
   - 不确定的边界，询问用户确认
3. 判断项目规模：
   - 小型项目（< ~50 代码文件）：可较完整生成，包括核心业务文件的文件级蓝图
   - 大型项目（50+ 代码文件）：只生成根蓝图和模块入口蓝图，文件级蓝图交给 align
4. 生成根蓝图 `.blueprint/README.md`，包含：
   - 项目概述（类型、技术栈、核心职责）
   - 模块地图（每个模块的路径和一句话职责描述）
   - 核心模块标记（建议优先 explore 的模块）
   - 蓝图使用说明（指向 explore 和 align）
5. 为每个模块目录生成入口蓝图 `.blueprint/{module}/README.md`，包含：
   - 模块职责概述
   - 模块内关键文件列表及一句话说明
   - 模块的上下游依赖关系
6. 生成文件级蓝图， 对于小型项目中所有文件，大型项目则只生成每个模块中核心业务逻辑的业务文件，严格遵循三段式模板。
7. 校验生成结果：镜像路径正确、模板格式一致、无多余内容。
8. 输出初始化报告。

## 蓝图模板

文件级蓝图严格遵循以下三段式结构。生成时必须按此格式，不得自行增减字段。

```markdown
# {文件名} 蓝图

## Metadata
- title: 蓝图标题，通常是类名或模块名
- type: 类型标识（class | module | service | controller | util）
- summary: 一句话描述主要职责和能力

## 关键方法单元（只有核心业务文件才会有）
每个方法单元包含：
- location: 代码位置（类名.方法名 或 函数名）
- purpose: 方法存在的目的，解决什么问题
- input: 参数类型和说明
- output: 返回值类型和说明
- core_steps: 核心步骤列表（关注业务逻辑，不是代码细节）

## 变更记录
- YYYY-MM-DD: 变更摘要
```

### 模板设计原则

1. **轻量优先**：不是所有文件都需要填满所有字段， 大部分文件应该只有Metadata，只有核心业务文件才会有关键方法单元，变更记录
2. **意图优先**：关注"为什么"而不是"怎么做"
3. **稳定优先**：记录架构层面的变化，不是实现细节

## 路径映射

代码文件与蓝图文件保持镜像关系：

- `bridge/mcp-server.cjs` → `.blueprint/bridge/mcp-server.md`
- `scripts/remind-load.mjs` → `.blueprint/scripts/remind-load.md`
- `skills/explore/SKILL.md` → `.blueprint/skills/explore/SKILL.md`

规则：代码路径去掉扩展名加 `.md`，放到 `.blueprint/` 前缀下。代码文件本身是 `.md` 时保持同名。

## 规则

- 先理解项目再生成蓝图，不盲目铺开
- 遇到不确定的模块边界或业务逻辑，询问用户确认
- 不做全量文件扫描，渐进式为主
- 蓝图只在 `.blueprint/` 目录，不修改项目代码目录
- 严格按模板生成，不自作主张增加内容
- 路径映射必须稳定，保持"代码 → 蓝图"关系可信
- 大型项目中途介入时，标记核心模块，其余交给 align 在会话结束时补齐
- 核心模块识别优先看：入口文件、高引用文件、业务目录（而非工具/配置目录）

- 模块地图摘要
