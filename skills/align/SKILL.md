# align - 蓝图对齐检查

## 目标

让蓝图持续可信，而不是只在任务开始时存在。

## 关注范围

优先检查本轮真正发生了“架构意图变化”的代码，而不是所有机械改动。

## 执行步骤

1. 识别本轮真正有意义的业务变化，只有具有业务意义的代码逻辑发生改变，才可能修改蓝图，忽略格式化、注释和纯机械调整。
2. 根据代码路径映射对应蓝图路径，记录缺失蓝图和疑似过期蓝图。
3. 对比代码与蓝图的职责、关键方法、输入输出和边界描述是否仍然一致。
4. 区分结果：
   - 无需更新
   - 需要补充变更记录
   - 需要修正职责或关键方法单元
   - 需要补建蓝图
5. 对于缺失蓝图的文件，基于本轮会话中已读取的代码理解，按三段式模板补建文件级蓝图。
6. 如果本轮适合只检查，则输出差异和建议；如果需要同步，则只做轻量同步，不做全量重写。
7. 输出最终对齐结果，并标记仍待处理的蓝图路径。

## 规则

- 关注意图漂移，不关注实现噪音
- 优先根据会话与 `git diff` 收缩检查范围
- 不因为模板存在就强行重写所有蓝图
- 路径映射必须稳定，保持“代码 → 蓝图”关系可信
- 历史蓝图过旧时，优先修正职责与关键方法，而不是扩写细节
- 补建蓝图时严格遵循 init 中定义的三段式模板（Metadata + 关键方法单元 + 变更记录）
- 只为本轮会话中实际接触过的文件补建蓝图，不扩大范围

## 输出结果

- 对齐状态（通过 / 警告 / 失败）
- 缺失或过期的蓝图文件
- 需要修正的职责或关键方法单元
- 建议同步或已完成同步的蓝图文件

## 蓝图模板

文件级蓝图严格遵循以下三段式结构。生成时必须按此格式，不得自行增减字段。

```markdown
# {文件名} 蓝图

## Metadata
- title: 蓝图标题，通常是类名或模块名
- type: 类型标识（class | module | service | controller | util）
- summary: 一句话描述主要职责和能力

## 关键方法单元（只有核心业务文件才会有）
每个方法单元包含：
- location: 代码位置（类名.方法名 或 函数名）
- purpose: 方法存在的目的，解决什么问题
- input: 参数类型和说明
- output: 返回值类型和说明
- core_steps: 核心步骤列表（关注业务逻辑，不是代码细节）

## 变更记录
- YYYY-MM-DD: 变更摘要
```
